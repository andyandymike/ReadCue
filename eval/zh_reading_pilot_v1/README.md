# 中文朗读规范化情境样例 v1

这是 ReadCue 在决定是否开展中文模型训练之前使用的 **72 条项目原创情境样例**。文本与候选答案均由 assistant 编写（`provenance=assistant_authored`），每条都标记 `human_reviewed=false`。它们不是抓取语料、真实用户日志、人工母语者已审数据或盲测集；自然的写法不代表已验证的真实需求。

这份样例用于发现可复查的差异、检查评测流程和评估后续采集方向。它不是一个有代表性的中文能力 benchmark，也不证明任何现成系统已经失败。当前不存在 ReadCue 模型结果。不存在以这份样例为依据的付费或训练授权。

## 范围与分组

本轮只评估 **完整句子的文本朗读规范化**，不输出拼音、音素或音频，不评估多音字消歧和 TTS 听感。

| track | 数量 | family | 用途 |
| --- | ---: | --- | --- |
| `core_tn` | 24 | calendar、clock_duration、money、measurement、percentage、count_ordinal | 明确数字、日期、金额、单位等常见 TN 范围 |
| `context_reading` | 24 | six_context、chat_digit_context、yyds_preserve、other_abbreviation、digit_identifiers、mixed_text | 相同数字在不同语境的读法、网络表达保留与混合文本 |
| `preservation` | 24 | ordinary_sentence、proper_names、literal_quotes、code_identifiers、product_models、latin_tokens | 正常词句、专名、引文、标识与型号的保真 |

共有 18 个 family，每个 4 条。各组不是独立随机采样，相近情境构成有意设计的对照；不能把 72 条当作 72 个独立用户需求。

`core_tn` 应单独报告，它与常见 TN 系统的任务范围更接近。其余两组含本项目明确约定的保留策略；如果某个现成系统并未声明支持该策略，其差异应报告为任务契约不一致，不直接宣传为该系统的通用能力缺陷。不要只给合并分数。

## 预先约定的读法

- 尽量忠实保留原句，只转换具有明确语义的常规数字和符号；不润色、纠错、翻译、补充解释或改变作者语气。
- 年份通常逐位读，明确金额、人数和单位数量按数值读；手机号式尾号、取件码和校验码逐位读。所有编号、专名和叙述情境均为编写样例，不对应真实账户或当事人。
- 网络赞叹 `666` 读作“六六六”，不展开为“太厉害了”；`233` 和 `88` 的网络用法也按逐位数字读法保留。数字表达在明确金额语境中按数值读。
- `yyds`、`awsl` 等缩写默认保持原样，不推测并输出中文释义。英文词、商品型号和代码标识保持原样，包括型号内部数字、大小写和下划线。这里只确定输出文本，不指定下游 TTS 怎样读英文。
- 一与幺、二与两、半点与三十分等在合理语境中提供多个完整句参考。参考集合并非穷尽所有合理汉语表达；未匹配结果需要人工复查后才能确认为内容错误。
- 不通过句内元指令告诉模型如何变换该句，避免将指令遵循混入 TN 对照。正文中的自然话语是待转换文本。
- 标点的等价全角/半角差异可以由统一评分器处理；不能为提高分数删除有语义的符号、下划线或区分型号的字符。其他等价处理须在运行前固定并留记录。

## 文件结构与推理隔离

`cases.jsonl` 使用 UTF-8，每行一个对象：

| 字段 | 含义 |
| --- | --- |
| `id` | 稳定样例编号 |
| `family` | 设计情境家族，仅离线分析 |
| `track` | 上述三种评测分组，仅离线分析 |
| `text` | 唯一逐样例推理输入 |
| `acceptable_outputs` | 离线评分使用的完整句参考数组 |
| `rationale` | 该样例与参考选择的设计说明，仅离线审查 |
| `provenance` | 固定为 `assistant_authored` |
| `human_reviewed` | 初始全部为 `false`，人工复核前不得宣称已审 |

系统可使用所有样例共享、事先固定的任务说明，但不得把 `acceptable_outputs`、`rationale`、`family` 或 `track` 传入模型，或依据这些字段逐样例选择规则、提示和后端。基线的规则和提示必须独立于当前样例答案构建。

## 版本、审查与用途边界

1. 在首次运行前记录本文件和 `cases.jsonl` 的 SHA-256、模型 revision、任务说明、规范化规则与运行配置。
2. 先冻结样例，再运行对照；保留原始输入和输出。列出参考未覆盖的合理读法、契约不一致及真正的内容错误，不能把完全匹配失败全部当作有害改写。
3. 审阅可由其他 assistant 协助，但这不等于人工复核；`human_reviewed` 只有实际人工逐条审查后才可变更，并需记录审查者、日期和变更。
4. 冻结后如果修复参考或读法策略，发布新版本并记录理由、旧新哈希以及受影响的样例；同时保留旧版分数，不为某个系统静默放宽参考。
5. **不得使用这份 pilot 训练模型或调参之后，仍把它称作独立评估。** 包括据此改提示、词典、规则或挑选检查点。发生这种使用后应明确标为开发集，并另建独立留出集。
6. 下一阶段需要有明确来源、许可和使用情境的真实需求样本，以及人工复核。当前人工编写 pilot 不能替代这些步骤，也不能用来宣称外域泛化、真实用户收益或语音听感提升。
